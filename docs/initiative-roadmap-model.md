# Initiative And Roadmap Model

## Purpose

This document defines how the product should turn a program baseline into actionable improvement work.

The roadmap is the main product output after onboarding. It translates current-state understanding into a practical sequence of improvements.

## Core Concept

The system should generate initiatives, not just findings.

A finding tells the consultant what is wrong or unsupported.

An initiative tells the consultant:

- what to improve
- why it matters
- what outcome it should create
- how hard it is likely to be
- what should happen first

## Initiative Structure

Each initiative should include:

- title
- summary
- targeted capabilities
- related systems or dependencies
- linked risk drivers
- related framework overlays
- expected outcomes
- suggested first steps
- evidence or validation expectations
- effort estimate
- cost estimate
- business impact
- resilience value
- urgency
- priority
- owner
- status

## Priority Model

Priority should not be a single severity label.

The system should rank initiatives using separate dimensions:

- risk reduction value
- resilience improvement value
- operational feasibility
- cost and effort
- business disruption
- contractual or framework urgency
- dependency ordering
- confidence in the underlying baseline

This allows output such as:

- do now
- do next
- plan this quarter
- strategic improvement later
- validate before committing

## Initiative Types

Typical initiative types include:

- foundational
- corrective
- resilience uplift
- operationalization
- evidence and validation
- maintenance improvement

Examples:

- establish an authoritative asset inventory
- formalize privileged access review
- validate backup restore procedures quarterly
- build incident response exercise cadence
- centralize logging for critical systems
- clarify managed service provider responsibilities

## Roadmap Layers

The roadmap should be visible in three layers.

### 1. Immediate Actions

Small, high-value steps that reduce uncertainty or risk quickly.

Examples:

- identify backup owners
- document critical systems
- confirm MFA coverage
- collect missing evidence for a claimed capability

### 2. Near-Term Initiatives

Work that should begin in the next planning horizon.

Examples:

- formalize vulnerability management workflow
- define incident response roles
- improve logging coverage for critical assets

### 3. Strategic Improvements

Larger efforts that may require budget, tooling, or organizational change.

Examples:

- identity platform consolidation
- endpoint management modernization
- vendor risk program formalization

## Relationship To Frameworks

Frameworks should influence initiative priority, but not dominate it.

A roadmap item can be important because:

- it materially reduces operational risk
- it improves recovery and resilience
- it is a prerequisite for multiple capabilities
- it supports an external framework requirement

The application should show all of those reasons, not only the framework reason.

## Maintenance Model

Not all security work should appear as a one-time initiative.

Some work belongs in recurring maintenance tasks:

- restore testing
- access reviews
- incident tabletop exercises
- vulnerability review cadence
- policy review cadence
- vendor review cadence

The roadmap should distinguish:

- build or fix work
- recurring keep-it-healthy work

## Suggested Workflow

1. derive initiative candidates from weak or low-confidence capabilities
2. group related gaps into practical chunks
3. identify dependencies and ordering
4. score each initiative across the priority dimensions
5. produce a recommended roadmap
6. let the consultant adjust the order and ownership

## Consultant Experience

The roadmap view should let the consultant:

- filter by capability
- filter by priority horizon
- understand why an initiative is recommended
- see what evidence or validation is still missing
- distinguish between quick wins and strategic work
- export a client-friendly version

## Initial V1 Output

The first version does not need full project management.

It should be enough to support:

- initiative list
- rationale and priority explanation
- expected outcomes
- suggested next steps
- rough effort and cost bands
- owner placeholder
- export-ready summary

## Relationship To Existing Assessment Work

Requirement-level findings can still feed roadmap generation.

They should be treated as one input source among several:

- onboarding answers
- capability reviews
- evidence gaps
- scans
- framework overlays
- consultant judgment

This keeps the roadmap tied to the client's real program instead of reducing everything to a control spreadsheet.
